# Logos Core Module Specifications — Independent Analysis at `6cac8335`

This document presents an independent analysis of the Logos Core module specifications on `draft/logos-core-module-specs` at commit **`6cac8335`** (`6cac8335af8cea0e5d4e2f9ccb2e584c5b27a7c2`, 2026-11-17, 13 `spec-*.md` files, 21,100 lines), using the release module catalogs (`logos-co/logos-modules-release` and `dlipicar/logos-modules-release`), application integration guide (`logos-co/logos-docs` PR #521), and LEZ node/wallet SDK requirements (`logos-co/rfp` PR #206: `RFP-027` + 6 appendices) as orientation for target use cases — assuming modules, SDKs, and surrounding designs can be freely adapted to the new Core.

**Scope.**
- Findings already established in the earlier specification reviews on this branch are not repeated here. This document covers strictly new findings at `6cac8335`:
  1. **Section 1 (`GF-01`–`GF-28`):** Contradictions, inconsistencies, and gaps in the Core specifications in isolation at `6cac8335`.
  2. **Section 2 (`GC-01`–`GC-08`):** Missing Core capabilities and specification blockers when porting catalog modules and supporting target SDK/application use cases on the new Core (even when modules and SDKs are rewritten cleanly for it).
  3. **Appendix A:** Summary of programmatic checks that passed cleanly at `6cac8335`.

**Conventions.**
- Short names: `cdCDDLe`, `COMMITMENT`, `HASH`, `INTERFACE`, `TRANSPORT`, `RUNTIME`, `CONFIG`, `LOADER`, `CA` (Capability Authority), `PM` (Package Manager), `SECURITY`, `BCP`, and `CREDENTIAL-STORE` (`spec-module-credential-store.md`, added in `6cac8335`).
- Every `l.N` line reference cites `draft/logos-core-module-specs` at `6cac8335`.

**Highest-impact blockers at `6cac8335`:**
- **`GF-01` & `GF-02` (Critical — `CREDENTIAL-STORE` vs `INTERFACE` & `CA`):** `CREDENTIAL-STORE` is an ordinary local module provider that MUST return `NOT_AUTHORISED` on slot/permission denials, while `INTERFACE` §5.1 (added in `6cac8335`) forbids providers from returning `LOGOS_ERR_NOT_AUTHORISED` and forces ABI callers to overwrite it with `LOGOS_ERR_MODULE`. Simultaneously, `CREDENTIAL-STORE` §2.2 requires evaluating and mid-method rechecking `logos.credential-store.administration` for the inbound caller via `CA`, while `CA` §§2, 3.5, and 10 forbid ordinary providers from calling `evaluate` for another consumer or using Runtime's protected binding.
- **`GF-08`–`GF-10` & `GC-03` (High — `extends` broken for interface upgrades, commitments, `logos.schema`, and real contract evolution):** Upgrading an implemented interface `I_1 -> I_2` replaces `root(I_1)` in `_implements` (duplicate interface namespaces are forbidden), causing `P_2` to fail `COMMITMENT` §9.1's `extends` rule (`every implemented-interface root of A is an implemented-interface root of B`); `COMMITMENT` §§4/8 and `HASH` §8 compute `value_root` under `root(B)` instead of selected `root(A)`; `INTERFACE` §2.6 rejects concrete `extends` entries when `primary` adds a new interface; `logos.schema` omits extended-contract routes; and `extends` still breaks on adding any optional field, enum variant, or even an unused type in an imported supporting schema.
- **`GF-14` (High — `RUNTIME` §9.3.1 Order of Checks contradictions):** Step 5 (`stale-revision`) runs before `CONFIG` §5 Row 1 (when no configuration binding exists) and before `RUNTIME` §9.3.18's `INVALID_PARAMS` check on name-selected facades (which have no `execution.revision`), while `RUNTIME` §9.3.4 l.2515 still mandates the shared invocation-error channel for stale revisions.
- **`GF-15`–`GF-17` (High — `SubscriptionEnd`, `logos_publish_fn`, and direct-mode queued events):** `TRANSPORT` §8.1 l.972 (`Unsubscribe` fails with `NOT_AUTHORISED` during termination) contradicts §5.1 l.755 (`Unsubscribe` after `SubscriptionEnd` succeeds) and strands `handler`/`user_data`; `logos_publish_fn`'s new return code creates a three-way size-limit conflict across `INTERFACE`, `RUNTIME`, and `TRANSPORT`; and `INTERFACE` §2.5's cross-thread event queue contradicts §2.9.3 l.2153 and lets a final `Response` overtake an earlier invocation-scoped `Event`.
- **`GF-24` & `GF-25` (High — C11/C++17 compilation & `logos_types.h` defects):** `clang -std=c11` and `clang++ -std=c++17` fail on `INTERFACE` §2.4 Rule 9 (`const const char**` for `[* tstr]` inputs and non-`const` `<type>** out_<name>` outputs) and on the verbatim `logos_types.h` listing (missing `#ifndef LOGOS_TYPES_H` include guard and literal `<module-C>` syntax at lines 3814 and 3818).
- **`GC-01`, `GC-02`, & `GC-05` (High — Missing Core capabilities for porting real modules & apps):** Banning `_sensitive` methods on `logos.remote.tls-tcp` and `logos.remote.quic` blocks remote secret-bearing operations, poisons every default (`access: {}`) remote route to any contract with even one `_sensitive` method, and leaves 1:1 invocation-scoped events unable to use `_sensitive`; `CREDENTIAL-STORE` covers only static host-provisioned service slots (no read, rotate, delete, KDF/unseal, dynamic user slots, or upgrade slot transfer, `GF-04`), leaving wallet/keystore/signer modules without a Core secret-storage or root-key capability; and browser extensions / web apps cannot connect to any Core Transport profile even on `localhost`.

## 1. Contradictions and Gaps in the Core Specifications at `6cac8335`

### 1.1 `LOGOS-MODULE-CREDENTIAL-STORE` and Cross-Spec Authority / ABI Contradictions

#### `GF-01` (Critical) — `CREDENTIAL-STORE` mandates returning `NOT_AUTHORISED` from native provider code, which `INTERFACE` §5.1 forbids and overwrites with `MODULE_ERROR`
- **Specs:** `CREDENTIAL-STORE` §1 l.29 (`"Credential Store is an ordinary local module provider using the existing identity, lifecycle, authority, routing, and invocation model"`), §2 l.55–56 (`"The provider MUST reject a call without authenticated context or from a module instance owned by another Runtime with NOT_AUTHORISED. The provider MUST reject an undeclared or unauthorized slot with NOT_AUTHORISED before accessing its backend or revealing its presence"`), §3 l.176 & l.199–200 (`logos.credential_store.error` and `administration_error` contain no authorization-denial arm), §3 l.308 (`"Authorization failures use NOT_AUTHORISED"`), §4.1 l.342 (`"The provider MUST reject requests without authenticated local caller context with NOT_AUTHORISED"`). Against: `INTERFACE` §5.1 l.3308–3312 (added in `6cac8335`: `"Provider code MAY return or complete with LOGOS_OK, LOGOS_ERR_METHOD_NOT_FOUND, LOGOS_ERR_INVALID_PARAMS, or LOGOS_ERR_MODULE. It MAY use LOGOS_ERR_CANCELLED only for an invocation whose cancellation is known at the provider boundary, and any other status code violates these rules. An ABI caller MUST validate a native provider result's status code, message and detail before forwarding them. A provider result violating these rules MUST be treated as LOGOS_ERR_MODULE, without forwarding its diagnostics or contract-response outputs"`).
- **Issue:** Runtime pre-dispatch route authorization (`CREDENTIAL-STORE` §1 l.31, §2 l.54) checks only method-call scope (`create`, `status`, `inspect`, etc.); it cannot enforce undeclared/unowned slot names in `create`/`status`, mid-method `logos.credential-store.administration` checks and pre-publication rechecks (§2.2 l.135), or local-Runtime caller checks on `status` and `inspect` (neither of which is marked `_sensitive` at l.163–172, so remote routes to them are permitted by `RUNTIME` §9.3.12 l.2939). When conforming Credential Store provider code returns `LOGOS_ERR_NOT_AUTHORISED`, a conforming Runtime or Module Host ABI caller MUST treat that return code as an ABI violation under `INTERFACE` §5.1 l.3308–3312 and rewrite it to `LOGOS_ERR_MODULE` (`MODULE_ERROR`). Both specifications cannot be satisfied simultaneously.
- **Suggested resolution:** Either add `"not-authorised"` to `logos.credential_store.error` and `logos.credential_store.administration_error` (matching `CA` §7 `logos.capability_authority.error_code`), or permit `LOGOS_ERR_NOT_AUTHORISED` in `INTERFACE` §5.1 l.3308 when a Logos-defined contract delegates subject/resource authorization enforcement to the provider under `CA` §3.5, subject to the non-revealing diagnostic rule at `INTERFACE` l.3313–3314.

#### `GF-02` (Critical) — Credential Store has no legal ABI or contract path to evaluate or mid-method recheck `logos.credential-store.administration` for an inbound caller
- **Specs:** `CREDENTIAL-STORE` §1 l.29, §2.2 l.96 (`"Administrative operations use the logos.credential-store.administration permission through the existing permission_scope defined by LOGOS-MODULE-CAPABILITY-AUTHORITY"`), l.132–135 (`"The protected invocation integration MUST evaluate the original authenticated caller's permission for the exact operation and assignment. It MUST NOT substitute the provider's authority or authenticate a caller from request fields. ... Permission MUST be checked before backend access and rechecked before durable publication or a secret-bearing response"`), l.139 (`"and the selected issuer version when one already exists"`). Against: `CA` §2 l.93 (`"On an ordinary routed call, Runtime MUST reject a supplied consumer that differs from the authenticated caller with NOT_AUTHORISED without dispatch"`), §3.5 l.417–421 (`"A permission enforced by a module provider MUST define how the authenticated enforcing provider obtains the applicable authorization for the checked subject, resource, and operation. ... This rule does not grant ordinary providers access to the Runtime's protected evaluate binding"`), §10 l.1421 (`"A provider-access grant for evaluate permits an ordinary consumer to request evaluation only with itself as consumer"`); `INTERFACE` §5.2 l.3544–3558 (`logos_invocation_context_vtable` exposes only `caller`, `is_cancelled`, and `publish`); `BCP` §3.3 l.202 (`"does not extend Runtime Control"`).
- **Issue:** Runtime cannot evaluate `logos.credential-store.administration` before dispatching an ordinary routed call to `logos_credential_store` because the evaluated scope depends on Credential-Store-internal assignment state (e.g., whether an issuer version already exists in `issue`, l.139; CA profile rules in `generate`, l.140) and MUST be **rechecked mid-execution** after key generation/decryption before durable publication or secret-bearing output (l.135). Yet inside `logos_credential_store` (an *"ordinary local module provider"*, l.29):
  1. calling `CA.evaluate` on a routed binding with `consumer` set to the inbound caller is rejected with `NOT_AUTHORISED` by `CA` §2 l.93 and §10 l.1421;
  2. giving `logos_credential_store` Runtime's protected `evaluate` binding is forbidden by `CA` §3.5 l.421;
  3. inspecting grants via `list_grants` is forbidden as an authorization substitute by `CA` §3.5 l.420; and
  4. neither `INTERFACE` (`logos_invocation_context_vtable`), `RUNTIME`, `CA`, nor `CREDENTIAL-STORE` defines any invocation callback or `CA` subject-evaluation method.
- **Suggested resolution:** Define the concrete mechanism mandated by `CA` §3.5 l.417 — either a `Capability Authority` method for authorized enforcing providers (where authenticated `consumer` is the enforcing provider checking `subject` + permission + constraints) or a permission-evaluation callback on `logos_invocation_context_vtable_t` mediated by Runtime's protected CA binding.

#### `GF-03` — Single-assignment, single-operation `logos.credential_administration.scope` collides with unique permission names in `PM` `requested_permissions` and `RUNTIME` §9.3.4 `permission_settings`
- **Specs:** `CREDENTIAL-STORE` §2.2 l.106–121 (`logos.credential_administration.scope` carries one `assignment` and one `operation`), §4.1 l.376 (`generate` with `certificate` `"requires both generate and issue permission on the target assignment"`), l.381 (`issue` `"requires issue permission on the exact issuer version and inspect permission on the exact target version"`), l.433 (`generate` + `inspect` for crash recovery). Against: `PM` §4 l.339 (`"Within one module declaration, ... requested permission names MUST each be unique"`); `RUNTIME` §9.3.4 l.2463–2465 (`"Permission names MUST be unique and ordered by their UTF-8 bytes. ... Omitted permissions are denied, including when the array is empty; declarations and grants MUST NOT bypass these limits"`).
- **Issue:** Every administrative scope uses the single permission name `"logos.credential-store.administration"`.
  1. Because `PM` `requested_permissions` enforces unique `permission` strings (`PM` l.339), a packaged module can declare at most **one** `logos.credential_administration.scope` (one assignment, one operation) — making it structurally impossible to declare the permissions needed for `issue` (two assignments/operations), self-signed `generate` (`generate` + `issue`), or `generate` + `inspect` recovery.
  2. In `RUNTIME` §9.3.4, `permission_settings` also enforces unique permission names and states unconditionally at l.2465 that omitted permissions are denied and *"declarations and grants MUST NOT bypass these limits"*. Under literal l.2465, `permission_settings` either blocks `"logos.credential-store.administration"` completely (when omitted from `permission_settings`) or caps any module instance to a single assignment and single operation, making `issue` and self-signed `generate` impossible even with multiple `CA` grants.
- **Suggested resolution:** Allow policy/manifest/settings constraints for `logos.credential-store.administration` to carry a canonically ordered non-empty list of `scope` entries (while keeping individual evaluated check requests single-scope), and state explicitly in `RUNTIME` §9.3.4 l.2465 and `CA` §3.3 l.368 whether `permission_settings` bounds only host/OS execution permissions or also provider-enforced `logos.*` permissions.

#### `GF-04` — Caller-owned slots (`create` / `status`) permanently strand credentials on package upgrades, deadlock dynamic `create_module` instances, and provide no deletion mechanism anywhere in the spec
- **Specs:** `CREDENTIAL-STORE` §1 l.35–36 (`"These methods provide no credential retrieval, enumeration, replacement, deletion, key generation, signing, or startup-delivery operation"`), §2 l.49 (`"For create and status, a slot is identified by the authenticated caller's Runtime and module-instance identities together with a credential name"`), l.58–61 (`"Protected deployment input MUST bind each permitted caller and name to one authoritative storage slot. Different caller identities MUST NOT alias the same slot. Module configuration, package declarations, and method authority MUST NOT create slot assignments or select host storage locations. A slot assignment MUST remain associated with the same owner across provider and host restart"`), §3 l.178–304 (neither caller-owned nor administrative methods include `delete`); `RUNTIME` §9.3.6 l.2558–2566 (`create_module` mints a fresh `module_instance_id`; upgrades do not reuse `module_instance_id`); `BCP` §5.3 l.400 (privacy/decommissioning disposal).
- **Issue:**
  1. **Permanent lockout on package upgrade:** Upgrading a package-backed module retires the old instance and creates a replacement instance with a new `module_instance_id` (`RUNTIME` l.2558–2566, l.3415). Unlike `state_dir` (`RUNTIME` §8 l.1384–1385) and `CONFIGURATION`, `CREDENTIAL-STORE` l.59 & l.61 forbid two `module_instance_id`s from ever binding to the same slot and provide no slot-migration path — permanently stranding every caller-owned credential on upgrade.
  2. **Dynamic `create_module` deadlock:** `create_module` generates a collision-resistant `module_instance_id` dynamically at run time (`RUNTIME` l.2558–2560), so static protected deployment input cannot pre-bind it before creation, while l.60 forbids configuration, package declarations, and method authority from creating slot bindings.
  3. **No deletion operation anywhere:** Neither caller-owned (`create`, `status`) nor administrative (`inspect`, `generate`, `issue`, `import`, `export`, `seal_unlock`) methods provide credential or slot deletion, leaving no contract path to wipe retired secrets on module removal (`BCP` l.400).
- **Suggested resolution:** Permit explicit authorized host/deployment slot migration from a retired `module_instance_id` to its replacement on upgrade (matching `RUNTIME` §8 l.1384–1385), allow authorized provisioning to bind slots at `create_module` time, and add an administrative `delete`/`retire` operation (or document host-side disposal).

#### `GF-05` — No startup credential-delivery path exists in `logos_module_init_input_t` for `direct` mode or multi-instance processes
- **Specs:** `CREDENTIAL-STORE` §1 l.36, l.42, §5 l.443 (`"Plaintext credentials MUST NOT enter ordinary module configuration, assigned persistent state, logs, audit records, diagnostics, responses, or events"`), l.459–462 (`"The host integration owns protected credential delivery to the selected component. ... Delivery does not use this contract's response channel"`); `INTERFACE` §5.2 l.3639–3649 (`logos_module_init_input_t`); `RUNTIME` §8 l.1398 (`"MUST NOT use process-global environment as per-instance state"`).
- **Issue:** After a module calls `logos_credential_store.create(name, value)` and restarts, how does portable module code read its credential? Retrieval over `logos_credential_store` is forbidden (`l.36`), passing credentials via `configuration_cbor` or `state_dir` is forbidden (`l.443`), per-instance environment variables (`$CREDENTIALS_DIRECTORY`) are forbidden (`RUNTIME` l.1398), and `logos_module_init_input_t` (`INTERFACE` l.3639–3649) provides only `(runtime_control, publish_user_data, publish, state_dir, configuration_cbor, invocation_access)` with **no** `credentials_dir` or credential-reader handle. On iOS/Android `direct_static` builds (`SECURITY` §11.5 l.474) and multi-instance desktop `direct` placements without per-unit OS filesystem namespaces, no portable Core mechanism exists to deliver the credential.
- **Suggested resolution:** Either add an optional per-instance credential-delivery handle/directory to `logos_module_init_input_t` or explicitly scope `CREDENTIAL-STORE` to OS-isolated host-activated placements with out-of-band filesystem/FD mounting.

#### `GF-06` — Permanent capacity exhaustion ("bricking") in `CREDENTIAL-STORE` §4.1: retired `operation_id` tombstones can never be freed under a mandatory finite `capacity` bound
- **Specs:** `CREDENTIAL-STORE` §4.1 l.422–426:
  > `"The provider MUST bound retained operation data and reject new admission with capacity before exhausting that bound. A provider that retires an operation's request or result MUST keep, under the same protection, the operation identifier, the information needed to compare a retried request, and the last established outcome state. Inspection of a retired operation and an identical retry MUST return unavailable; a conflicting retry MUST return conflict. A retired operation MUST NOT be reported as absent, as pending, or with a newly generated result. Retiring a record MUST NOT make its identifier available for a new operation or turn an uncertain outcome into absent."`
- **Issue:** Because `operation_id` is an arbitrary caller-chosen string (`tstr .size (1..128)`) and l.423–426 require permanently retaining `(operation_id, request-comparison digest, outcome)` so retired IDs never become `absent` and always distinguish `unavailable` vs `conflict`, every `generate` or `import` consumes non-reclaimable storage forever. Under l.422's mandatory finite bound, any long-lived deployment performing periodic key/certificate rotation eventually fills its bound with retired tombstones and **permanently rejects all future `generate` and `import` calls with `capacity`**.
- **Suggested resolution:** Introduce an assignment operation epoch or monotonic generation floor (advancing the epoch invalidates older epochs wholesale with `unavailable` without retaining unbounded per-`operation_id` state, analogous to `RUNTIME` §9.3.13 l.3086).

#### `GF-07` — Validation, audit-sensitivity, and cross-provider `issue` gaps in `CREDENTIAL-STORE`
1. **Ambiguous error outcomes (`CREDENTIAL-STORE` §2 l.50, §2.2 l.147, §3 l.195, l.212, l.307, §4.1 l.343, l.351, l.375–377, l.391):**
   - `certificate_parameters.validity_seconds` is `uint64` (`l.212`, admitting `0`), while §2.2 l.147 requires *"evaluated validity MUST be positive"* and §3 l.307 lists *"Invalid request shapes, names, identifiers, and certificate constraint sets MUST fail with INVALID_PARAMS"* without mentioning `validity_seconds == 0` (leaving `0` ambiguous between `INVALID_PARAMS` and `NOT_AUTHORISED`).
   - Line 307 mandates `INVALID_PARAMS` for off-schema lexical/ordering checks (`name` charset `[a-z0-9-]` at l.50; unordered/duplicate `names`/`purposes` sets at l.375) without adding `"without validation detail"` — conflicting with `INTERFACE` §5.1 l.3295–3307 (contrast `RUNTIME` l.2464 & l.2933).
   - `identifier` (`l.195`, `tstr .size (1..128)`) has no lexical grammar in §2, leaving `"Invalid ... identifiers ... MUST fail with INVALID_PARAMS"` (`l.307`) vs `"opaque values compared exactly"` (`l.343`) ambiguous on `/`, `..`, or control characters; and l.377/l.391 do not state whether a profile-disallowed self-signed `certificate` or rejected `format` returns `{ error: "unsupported" }` or `INVALID_PARAMS`.
2. **Unspecified `CA` §9 audit sensitivity of `logos.credential_administration.scope` (`CREDENTIAL-STORE` §2.2 l.106–121, l.139 & §3 l.167, l.169 vs `CA` §9 l.1184–1185, l.1384–1386):** `generate_request` and `issue_request` are marked `_sensitive`, yet evaluating `logos.credential-store.administration` copies `assignment`, `version`, `subjects`, `names`, `purposes`, and `validity_seconds` into `permission_scope.constraints`, which `CA` §9 retains verbatim in `evaluate` audit records unless classified as sensitive constraint values (which fail with `authority-unavailable` without explicit sensitive-audit policy, `CA` l.1386). `CREDENTIAL-STORE` never states whether `logos.credential_administration.scope` is a sensitive constraint under `CA` §9.
3. **Cross-provider `issue` bridge (`CREDENTIAL-STORE` §4.1 l.381–383, §5 l.453 vs `CA` §2 l.101–102 & `BCP` §5.4 l.374):** When CA `assignment` (`P1`) and `target_assignment` (`P2`) live on separate Credential Store instances with isolated backends (`l.383, l.453`), `P1` cannot call `P2.inspect` over a Logos route without substituting `P1`'s caller identity (`CA` l.101–102, forbidden by `CREDENTIAL-STORE` l.133). The required host "protected assignment integration" is omitted from `BCP` §5.4 l.374.

### 1.2 Verified Contract Extensions (`extends`) and Package Release Compatibility

#### `GF-08` (High) — Upgrading an implemented interface (`I_1 -> I_2`) prevents a concrete module's primary contract (`P_2`) from extending `P_1`, breaking `PM` §11 SemVer compatibility
- **Specs:** `COMMITMENT` §3.1 l.290 & §9.1 l.963 (`"Two implemented-interface roots whose documents declare the same interface namespace are invalid"`), §9.1 l.966–973 (`"A contract B extends a contract A when all of the following hold: ... every implemented-interface root of A is an implemented-interface root of B"`); `INTERFACE` §2.6 l.1712 (`"MUST reject ... duplicate interface namespace"`); `PM` §11 l.1236 (`"A release within the range that a compatible requirement on an earlier release accepts MUST provide every contract that the earlier release provides and MAY provide additional contracts"`).
- **Issue:** A concrete module contract commits to its exact `_implements` roots in `schema-root-payload` field `4` (`COMMITMENT` §9.1 l.961–963). Suppose module `M` `1.0.0` has primary contract `P_1` with `_implements = [root(I_1)]`, and in `1.1.0` interface `I_2` compatibly extends `I_1` (same interface namespace, `root(I_2) != root(I_1)`). `P_2` **cannot** list both `root(I_1)` and `root(I_2)` in `_implements` (`COMMITMENT` l.290, l.963: duplicate interface namespace). Replacing `root(I_1)` with `root(I_2)` in `P_2._implements` (and placing `I_1` in `extends`) means `root(I_1)` is an implemented-interface root of `P_1` that is **not** an implemented-interface root of `P_2`. Under `COMMITMENT` §9.1 l.972, `P_2` **does not extend** `P_1`, so `M` `1.1.0` cannot preserve `P_1` in `extends` and violates `PM` §11 l.1236!
- **Suggested resolution:** Relax bullet 5 of `COMMITMENT` §9.1 l.972 so that for every implemented-interface root of `A`, `B` has an implemented-interface root that either equals it or extends it under **Contract extension** (established from the supplied interface documents in `INTERFACE` §2.6 and `PM` §4).

#### `GF-09` (High) — Value-commitment and verified-view `schema_root` mismatch on routes selecting an extended contract
- **Specs:** `COMMITMENT` §4 l.496–500 & §8 l.806–813 (`"For a primary module method, the defining schema root is the concrete module schema root. For an implemented interface method, the defining schema root is the implemented interface schema root"` / `"The same decoded CBOR data under different schema roots ... MUST NOT be treated as the same canonical value commitment"`); `HASH` §8 l.999–1000 & l.1093–1095 (`"A concrete provider schema root is checked here only when the method itself is defined by that concrete provider schema"`); `INTERFACE` §2.6 l.1722. Against: `TRANSPORT` §4.1 l.634 (`"The defining schema root is the session's selected contract root except for the well-known logos.schema method"`) and `CA` §9 l.1245–1247 / §9.1 l.1346–1348.
- **Issue:** Every physical value-commitment node embeds the 32-byte defining `schema_root` in field `1` (`HASH` §7.4, l.1105). When provider `P` exposes primary contract `B` and extended contract `A` (`root(A) != root(B)`), and consumer `C` invokes method `m` on a route established for `A`, `value_root` under `root(A)` differs from `value_root` under `root(B)` for identical CBOR bytes. `TRANSPORT` §4.1 l.634 and `CA` §9 l.1245–1247 compute `value_root` under `root(A)`, whereas `COMMITMENT` §§4/8 and `HASH` §8 l.999–1000, l.1093–1095 were not updated from the pre-`extends` two-case wording (and `INTERFACE` §2.6 l.1722 is ambiguous because `m` occurs in both `B` and `A`).
- **Suggested resolution:** Update `COMMITMENT` §§4 & 8, `HASH` §8 l.999–1000 & l.1093–1095, and `INTERFACE` §2.6 l.1722 so the defining schema root on an exact-contract route is the route's selected contract root (primary, implemented interface, or extended concrete/interface), except `logos.schema`.

#### `GF-10` (High) — `provider-call-surface` validation (`INTERFACE` §2.6), `logos.schema` (`INTERFACE` §5.1), `RUNTIME`, and `TRANSPORT` fail or omit rules for `extends`
1. **Unused-interface rejection when validating concrete `extends` entries (`INTERFACE` §1.1 l.113, §2.6 l.1694 & l.1716, §5.3 l.3998):** `COMMITMENT` §9.1 l.972 permits `primary` (`P_2`) to add new `_implements` interfaces (`[I_1, I_new]`) not present in `P_1` (`[I_1]` or empty). `provider-contract-schema` (`l.1660–1664`) has no per-entry `interface_schemas`, and `l.1716` states `"The interface entries provide the exact resolved _implements set used when constructing and validating the primary contract"`. Passing `interfaces` (`[I_1, I_new]`) when validating `P_1` under `l.1694` triggers `INTERFACE` §1.1 l.113 / §5.3 l.3998 rejection (`"includes an unused supplied interface"`).

#### `GF-15` (High) — Five defects in `SubscriptionEnd` (kind `9`) and `observe_subscription_end`
- **Specs:** `TRANSPORT` §1.3 l.231–235, §3.4 l.569–573 & l.583–584, §5.1 l.731 & l.752–756, §8.1 l.969 & l.972; `INTERFACE` §2.5 l.1416–1438 & l.1473–1485.
- **Defects:**
  1. **`TRANSPORT` §8.1 l.972 contradicts §5.1 l.755 and strands `handler` / `user_data`:** During authority-expiry/revocation termination (`§8.1` l.969, while an in-flight call finishes bounded completion), `§8.1` l.972 mandates that `Unsubscribe` fail with `NOT_AUTHORISED` without changing subscription state, whereas `§5.1` l.755 mandates that `Unsubscribe` after `SubscriptionEnd` succeed! #### `GF-16` (High) — `logos_publish_fn` return code creates a three-way size-limit contradiction across `INTERFACE` §5.2, `RUNTIME` §7.3, and `TRANSPORT` §2.1
- **Specs:** `INTERFACE` §5.2 l.3351–3352 (`"The publish callback returns LOGOS_OK when the event name is declared by the publishing module's contracts and the event data conforms to that event's data type and size limits, and INVALID_PARAMS otherwise. #### `GF-17` (High) — Direct-mode cross-thread queued subscription delivery (`INTERFACE` §2.5) contradicts `§2.9.3`, reorders final `Response` ahead of scoped `Event`, and enables infinite publisher starvation
- **Specs:** `INTERFACE` §2.5 l.1406–1408 (`"When a direct publication reaches a subscription whose handler invocation is active on another thread, the binding MUST queue that delivery with a copy of its event data instead of waiting"`), §2.8 l.1920 (`"Except for a delivery queued under Section 2.5..."`), §2.9.3 l.2153 (`"Every direct callback actually admitted by this publication MUST return before publish returns"`); `RUNTIME` §7.3.1 l.1194–1200 (`"No new scoped-event commitment is permitted after terminal Response commitment"`).

  1. `INTERFACE` §2.9.3 l.2153 was not updated with §2.8 l.1920's queueing carve-out: when worker thread `T2` calls `invocation->vtable->publish(ev2)` while `T1` is inside subscription `S`'s callback, `T2` queues `ev2` and returns immediately (violating `§2.9.3` l.2153), and if `T2` then completes the call with its final `Response`, the consumer receives the terminal `Response` on `T2` **before** `T1` delivers `ev2` (violating `RUNTIME` §7.3.1 l.1194–1200 and Transport ordering).

While `T1` runs a 5 ms handler, a second thread `T2` publishing every 4 ms returns instantaneously each time at `queue_len == 1` (never reaching `§2.5` l.1473's pending-delivery bound and bypassing `§2.8` backpressure), trapping `T1` in `§2.5` l.1407's drain loop indefinitely so `T1` can never return or reach `_MODULE_destroy` quiescence.
- **Suggested resolution:** Add the §2.5 exception to `INTERFACE` §2.9.3 l.2153, order direct async completion callbacks behind already-queued scoped events on the same invocation path (`RUNTIME` §7.3.1), and bound cumulative stolen deliveries drained per outer handler entry.

1. **`CA` §7 denial-code precedence (`CA` §7 l.785–794):** (a) Line 793 includes `contract` in *"the action"* for `runtime-control` scopes, **not** for `provider-access` (`kind="provider-access", action="call"`): holding a grant to `"call"` *any single contract `X`* causes calls to *every ungranted contract `Y`* to return `scope-denied` instead of `not-granted`! (b) Applying l.791–792 to `issue_grant(consumer=Admin, target=Worker, scopes=[S])` matches `Admin`'s own operational self-grants (`target=Admin`), returning `scope-denied` or `grant-revoked` instead of `not-granted`. (c) Existential `"as a requested scope"` (`l.792`) vs universal `"every requested scope"` (`l.786`) misclassifies multi-scope execution checks with an ungranted permission as `scope-denied`.
2. **`CA` `query_audit` > 16 MiB (`CA` §9 l.1159 vs l.1199–1201):** Each audit record's `scopes` may be up to 4 MiB (`l.1199`), and `query_audit` returns up to 1,000 matching records (`l.1159`) without `list_grants`'s 16 MiB message-ceiling truncation rule (`CA` §6 l.702) — so just 4 large records cause `query_audit` to fail with `MODULE_ERROR`.
3. **Selector-scoped Runtime Control subscriptions & `provider_export_record` (`CA` §3.2 l.301–305 & §5 l.556 vs `RUNTIME` §9.3.2 l.1936–1940, §9.3.15 l.3277–3280):** `logos_runtime_control_vtable.subscribe` carries only `event_name`, so under `CA` l.301 & l.556 any `runtime_control_scope` narrowed by `modules`, `instances`, `providers`, or `routes` rejects `subscribe` activation instead of filtering delivered events; likewise `provider_export_record` lacks `module` and `instance` fields, so `modules`/`instances`-scoped grants never match (`l.305`).
4. **`PM` `unsupported-manifest` & signer-replacement defects (`PM` §4.1 l.437, §4.3 l.565, §8 l.1067 & l.1074, §15 l.1685–1690 & l.1705–1706, §16 l.1896):** (a) `PM` §8 l.1067 & l.1074 allow validating `manifest.cbor` (`-> invalid-package`) before §4.3 `manifest.cose` (`-> unsupported-manifest`); (b) `manifest_commitment` (`l.1896`) pins literal `"logos.commitment-model.2026-10"`, so future commitment-model packages fail with `signature-verification-failed` before `unsupported-manifest`, and `installed_package_record` / `get_runtime_handoff` (`§15` l.1662–1665) have no serialization or error rule for retained unsupported-manifest records (`§11` l.1218); (c) a no-op `update_package` (`l.1706`) succeeds on an installed package whose signer was revoked, violating `§4.1` l.437, while `install_package` signer rotation (`l.1686–1689`) fails ~50% of the time without `source` (due to lexicographic `package_source` tie-breaking at `l.1330`) and leaves `installed_package_record.source` mismatched with the new `signer`.

### 1.4 C11/C++17 ABI, Bidirectional C↔CDDL Mapping, `COMMITMENT`, `HASH`, `cdCDDLe`, and `SECURITY`/`BCP`

#### `GF-24` (High) — `INTERFACE` §2.4 Rule 9 fails C++17 compilation (`const const char**` on `[* tstr]` inputs and discarded `const` on list output parameters)
- **Specs:** `INTERFACE` §2.2 l.885 (`tstr` -> `const char*`), §2.3 l.974–976 (`[* tstr]` -> `const char* const* items`), §2.4 Rule 9 l.1253–1254 (`"9. A variable-length list input uses adjacent const <type>* in_<name> and size_t in_<name>_count parameters. Its output uses adjacent <type>** out_<name> and size_t* out_<name>_count parameters"`), §2.7.1 l.1835 (`"Static storage MAY back a response without a resource release operation"`), §3.1 l.2212.
- **Compiler-verified defects (`clang -std=c11`, `clang++ -std=c++17`):**
  1. For `[* tstr]`, `<type>` is `const char*` (`l.885`). Literal substitution into `const <type>* in_<name>` (`l.1253`, `l.2212`) produces `const const char** in_<name>`, which is a **hard C++17 syntax error** (`error: duplicate 'const' declaration specifier`, C++ `[dcl.type.cv]`) and leaves the outer pointer array mutable (`const char**` instead of `const char* const*` in §2.3 l.974).
  2. Unlike §2.3 struct lists (`const <elem>* items`) and §2.4 Rules 6 & 8 (`const char**`, `const uint8_t**`), Rule 9 outputs use `<type>** out_<name>` (`uint64_t**`, `logos_ns_Rec_t**`, `const char***`), omitting `const` on pointee elements so a C++17 provider returning `static const uint64_t k_items[] = ...` (`§2.7.1` l.1835) **fails to compile**.
- **Suggested resolution:** Specify `const <elem>* in_<name>` (`const char* const*` for `tstr`) and `const <elem>** out_<name>` (`const uint64_t**`, `const logos_T_t**`, `const char* const**`) in §2.4 Rule 9 and §3.1.

#### `GF-25` (High) — Missing C mapping for named reference aliases (`A = B`), uncompilable verbatim `logos_types.h` listing, and `logos_bstr_size_<min>_<max>_t` round-trip break
1. **Named reference aliases (`A = B`) omitted from `INTERFACE` §§2.3 & 3.4 (`INTERFACE` l.993–1001, l.1036–1047, l.2444–2482; `COMMITMENT` §2.2 l.191 & B.1 l.1724; `HASH` B.4 l.1294–1305):** Valid schemas in `COMMITMENT` B.1 (`a.x = a.y`) and `HASH` B.4 (`types.alias = types.record`, `a.import = types.alias`) declare named types whose bodies are local or imported references, yet §2.3 l.993–1001 and §3.4 omit `typedef logos_<target>_t logos_<ns>_<Alias>_t;`, and §2.3 l.1036 builds the recursion graph *"over every generated aggregate declaration"*, breaking recursive cycles that pass through a local alias (`m.link = m.node`, `m.node = { ? next: m.link, value: uint64 }`).
2. **Verbatim `logos_types.h` fails C11/C++17 compilation (`INTERFACE` §2 l.624, §5.2 l.3325–3326, l.3373–3823):**
   - Lines 3325–3326 instruct tools to copy the listing verbatim (`"a tool copies them and does not derive them"`), yet lines 3814 and 3818 inside the `logos_types.h` code block contain literal angle-bracket placeholders (`logos_<module-C>_MODULE_async_api`, `logos_<module-C>_MODULE_free`) — a C11/C++17 syntax error.
   - `logos_types.h` (l.3373–3823) has **no `#ifndef LOGOS_TYPES_H` include guard**, while every generated entry and reusable dependency header MUST `#include "logos_types.h"` outside its guard (`§2` l.624) — causing duplicate enum/struct/inline-function redefinition errors whenever two generated headers are included in one translation unit!
   - `logos_types.h` l.3432 defines `typedef const uint8_t* logos_bstr_size_1_4096_t;`, leaving ambiguous under l.3326 vs §2 l.611 whether generated headers for schemas using `bstr .size (1..4096)` (`PM` l.312, `CREDENTIAL-STORE` l.488) re-emit or suppress that typedef.
3. **Equal-bound `logos_bstr_size_32_32_t` breaks §3.8 C→CDDL→C round-trip (`INTERFACE` §2.2 l.912–926, §3.1 l.2204–2205; `cdCDDLe` §7.4 l.325):** Neither §2.2 nor §3.1 requires `<min> < <max>`. A C header using `logos_bstr_size_32_32_t` + `size_t len` maps to `bstr .size (32..32)`, canonicalizes to `bstr .size 32` (`cdCDDLe` l.325), and regenerates in `H'` as `uint8_t[32]` **without `size_t len`**, breaking `INTERFACE` §3.8 ABI preservation! (Also `INTERFACE` §2.2 l.912 omits `"except for zero itself"` for `0_512`, and `INTERFACE` §3.3 l.2394–2395 / l.2439 misses §3.4 l.2475's `in_has_<field>` rule before `in_<field>_0` for optional inline-tuple method inputs.)

#### `GF-26` — `COMMITMENT` vs `HASH` schema-identity divergence on absent optional reference fields (`? f: T`), reference lists (`[* T]`), and reference choices (`T1 / T2`)
- **Specs:** `COMMITMENT` §4 l.472–474, §8 l.886–895, §9.3 l.1221–1245 & l.1261–1267 vs `HASH` §7.3 l.592, §7.4 l.653–656, l.660–689, l.713–720.
- **Issue:**
  1. For an absent optional field `? f: T`, `HASH` §7.4 l.653–656 + §7.3 l.592 set `absent-payload` field `2` to `"the identity of the field's value schema"` — the referring leaf hash `S_leaf(map, [field "f"])` (which is also required when `T` is an imported reference, since `absent-payload` has no `reference-value-payload` wrapper and its field `1` is the map's document root!). By contrast, `COMMITMENT` §9.3 l.1221–1231 wraps `absent-value` inside `field-value`, and `COMMITMENT` §8 l.887–888 assigns `absent-value.1 = S_node(T)` for a local reference while leaving imported-reference `absent-value.1` undefined.
  2. Neither spec states explicitly for `[* T]` (`T` a local alias, e.g. `T = uint64`) and `T1 / T2` whether `list-payload.3` (`element schema identity`) and `choice-payload.4` (`selected arm schema identity`) hold the referring container leaf `S_leaf` while `child-record.3` holds `S_node(T)`, nor whether `[* T]` for a local scalar alias `T = uint64` uses `packed-scalar-list-chunk-payload` (`HASH` §7.4 l.680, which omits per-element `child-record`s!) or ordinary `list-chunk-payload`. None of the test vectors in `COMMITMENT` or `HASH` exercise `? opt_ref`, `[* alias]`, or `choice`.

#### `GF-27` — `HASH` Appendix B.4 `N1..N8` complete-view claim, string-range verification gaps (`HASH` §8 Step 4), and `cdCDDLe` external-context decoder/prelude gaps
1. **`HASH` Appendix B.4 (`l.1374–1388`):** Claims that for `N1..N8`, *"both the complete view and the indicated partial view MUST be rejected despite their internally consistent hashes."* In a complete view (`path = []`), `proof-material` is empty (`l.1033`) and `disclosed-value` is a semantic `normalized-value-root` (`l.943`) containing **no** physical payload context fields — so keeping `disclosed-value` unchanged (`l.1375`) recomputes valid `a0 = 2f6aa6e4...` and fails by ordinary root mismatch at Step 7 (hashes are **not** internally consistent with the mutated root; likewise in `N1`'s partial view `amount, value`, `n` is the disclosed semantic leaf rather than proof material).

3. **`cdCDDLe` external-context & prelude gaps (`cdCDDLe` §6 l.232–236, §8 l.387–395, §10 l.572–585, §12 l.617–634):** `6cac8335` added external-context `type-reference` resolution in §6 l.235–236, but left undefined how standalone CBOR decoders/checkers (§8, §10, §12 `cdcddle-vector`) validate external `type-reference`s, and failed to forbid §5.1 primitive keywords (`{0: 3, 1: "uint"|"bool"|"tstr"|"bstr"}`) in `type-reference.1` or RFC 8610 Appendix D prelude names in `cdcddle-type-rule.1` during CBOR decoding.

## 2. Missing Core Capabilities for Porting Catalog Modules and Target Use Cases

This section evaluates whether the use cases represented by the 47-module release catalogs, application SDK guide, and node/wallet RFPs can be cleanly ported to Logos Core at `6cac8335` assuming modules, contracts, and SDKs are freely adapted to the new model. Legacy module implementation issues that can be resolved by refactoring module code, as well as capability trade-offs already established in earlier reviews, are omitted. Each item below identifies a capability that the Core specifications themselves currently lack or block.

#### `GC-01` — Remote `_sensitive` ban (`6cac8335`) prevents remote secret-bearing operations, poisons default (`access: {}`) remote routes on mixed contracts, and excludes 1:1 invocation-scoped events
- **Core specs:** `TRANSPORT` §8.4 l.1188–1189 (`"An ordinary provider session under logos.remote.tls-tcp or logos.remote.quic MUST NOT be established for a route that permits a method whose request or response is marked _sensitive"`); `RUNTIME` §9.3.1 l.1808, §9.3.12 l.2935 (`"An absent method list permits every method in the selected contract"`) & l.2939; `BCP` §5 l.267–268 (`logos.remote.tls-tcp` and `logos.remote.quic` are the **only** defined remote profiles); `INTERFACE` §1.4.1 l.377, §1.5 l.423–424 (`_sensitive` forbidden on events).
- **Use cases affected:** Controlling a home node's wallet, signer, keystore, LEZ private-account manager, or credential store from a remote phone/desktop Runtime; calling public read methods on a remote module whose contract also contains administrative/unlock methods; streaming decrypted messages or private wallet updates over a 1:1 `watch` stream.
- **Core capability gaps:**
  1. **No remote profile can carry `_sensitive` calls:** Even over an enrolled mutual-TLS 1.3 + RFC 9266 channel-bound remote Runtime session, *zero* `_sensitive` methods can be invoked remotely in Core (`INTERFACE` §1 Execution-Boundary Invariance `l.45–62` ceases to hold for `_sensitive` methods). Ported wallet/node/admin modules must either **drop `_sensitive`** (forfeiting local buffer-hygiene and audit commitment-retention protections, `INTERFACE` l.377) or forego remote Core invocation of any password-, seed-, key-, or token-bearing method.
  2. **Mixed-contract poison pill on default routes:** Because `access: {}` requests every method in the contract (`RUNTIME` l.2935), marking **even one admin/unlock method** `_sensitive` causes **every default `access: {}` remote route to that contract to fail with `INVALID_PARAMS`** (`GF-20`), even when the remote caller only invokes public read methods — forcing module authors to split every mixed module surface into separate public and sensitive contracts (or forcing every consumer to enumerate non-sensitive method roots).
  3. **No `_sensitive` protection for 1:1 invocation-scoped events:** When porting messaging (`chat`, `delivery`) or private wallet modules away from broadcast events to a 1:1 invocation-scoped `watch` stream (`RUNTIME` §7.3.1) so decrypted messages reach only the authenticated caller, `INTERFACE` §1.5 (`l.423–424`) still forbids marking *any* event `_sensitive` — leaving streamed confidential payloads without `_sensitive` zeroization or audit-commitment suppression (`INTERFACE` l.377).

#### `GC-02` — `LOGOS-MODULE-CREDENTIAL-STORE` (`6cac8335`) supports only static host-provisioned service slots and provides no Core capability for dynamic module-managed secrets or state-encryption root keys
- **Core specs:** `CREDENTIAL-STORE` §1 l.35–36 & l.41–42, §2 l.49 & l.56–61, §4.1 l.356, §5 l.443; `CONFIG` §1 l.57; `INTERFACE` §5.2 l.3639–3649.
- **Use cases affected:** Porting wallet, keystore, signer-manager, Keycard-pairing, and authenticated RPC-proxy modules that create, unlock, rotate, back up, and delete user accounts, BIP-39 seeds, hardware pairings, or upstream API keys at run time, or derive domain-separated symmetric keys (`data_key`) to encrypt SQLCipher / vault databases in `state_dir`.
- **Core capability gaps:** As defined in `6cac8335`, even cleanly rewritten wallet, keystore, and authenticated-proxy modules cannot use `logos_credential_store`:
  1. **Write-once caller-owned slots with no read, rotate, list, or delete:** Caller-owned methods are strictly `create` (which rejects existing names with `"already-exists"`, `l.356`) and `status` (`l.35–36`); neither caller-owned nor administrative surfaces define `delete` anywhere in the spec (`GF-04`), so user credential rotation, account removal, Keycard re-pairing, and data wipe cannot be implemented over `CREDENTIAL-STORE`.
  2. **Static protected-deployment slot bindings (`l.56–60`):** Requiring host deployment input to pre-bind every `(caller, name)` slot prevents dynamic creation of user wallets, accounts, pairings, or user-configured API keys at run time (and orphans slots across package upgrades when `module_instance_id` changes, `GF-04`).
  3. **No unseal / KDF / root-key capability for `state_dir` encryption:** Because `CONFIG` (`l.57`) and `CREDENTIAL-STORE` (`l.443`) forbid plaintext credentials in configuration or `state_dir`, `CREDENTIAL-STORE` provides no read, unseal, or key-derivation method (`l.36, 41`), `logos_module_init_input_t` has no portable startup credential-delivery handle (`GF-05`), and Core defines no OS-keychain permission profile, a ported keystore or encrypted-database module has **no Core-backed root key** to protect secrets at rest in `state_dir` without requiring an interactive user passphrase on every start.

#### `GC-03` — Contract extension (`extends`, `6cac8335`) cannot support optional-field additions, forward-compatible state/error enums, or shared supporting-schema additions
- **Core specs:** `COMMITMENT` §9.1 l.966–976 & l.979–982; `INTERFACE` §1.1 l.97–104, §1.2 l.204, §2.6 l.1700–1706; `TRANSPORT` §4.1 l.645–664.
- **Use cases affected:** Evolving node, indexer, storage, and messaging contracts across compatible releases — adding optional parameters/fields (pagination cursors, filters, fee metadata), introducing new sync-health states or confirmation tiers that older clients can treat as unknown without disconnecting, and adding types to shared supporting schemas.
- **Core capability gaps:**
  1. **Optional fields break `extends`:** `COMMITMENT` §9.1 (`l.971`) requires every `schema-declaration` of `A` to appear in `B` with the **identical** body; adding `? field: T` to any existing request, response, event, or shared record invalidates `B extends A` and forces `method_v2`, `method_v3` proliferation.
  2. **Forward-compatible enums are impossible and session-fatal:** Adding an arm to an existing status, confirmation, or domain-error choice breaks `extends`, and emitting an unrecognized variant on an older route triggers `ProtocolError INVALID_PARAMS` + **full provider-session closure** (`TRANSPORT` §4.1 l.661–664) rather than allowing unknown-variant fallback.
  3. **Direct supporting-schema freeze trap:** Although `INTERFACE` §1.1 (`l.97–104`) excluded *transitive* supporting-schema imports so changes would not break `extends`, every *direct* imported-type node embeds `schema-import = { 0: schema-root, 1: schema-subtree-root }` (`COMMITMENT` §9.1 l.979–982). Adding **even one unused type** to an imported supporting schema changes `schema-root` (`0`) and breaks `extends` for every contract importing *any* type from it — while `INTERFACE` §2.6 (`l.1700–1706`) requires all `supporting_schemas` across `primary`, `interfaces`, and `extends` on one provider to have distinct namespaces, making it illegal for one provider to carry `v1` (importing `types` v1) in `extends` and `v2` (importing `types` v2) in `primary`.

#### `GC-04` — Filtered/replayable streams ported to invocation-scoped `watch` calls lack synchronous stop/cleanup quiescence and per-stream backpressure isolation
- **Core specs:** `TRANSPORT` §5.1 l.700–785 (especially `l.753`), §5.2 l.792–801, §5.3 l.838, §6 l.857–858; `INTERFACE` §2.5 l.1416–1420, §2.9.2 l.2041–2042.
- **Use cases affected:** Block, event, and message streams that require filter arguments (account, topic, program/selector) or gapless historical replay from a starting height/cursor into live delivery, plus deterministic server/FFI resource release on unsubscribe while unary RPCs share the same route.
- **Core capability gaps:** Because Core `Subscribe` (`{ id, kind: 3, event }`) takes zero parameters and provides no replay (`TRANSPORT` l.783–784), porting parameterized/replayable subscriptions requires Core's open-ended invocation-scoped async `watch` call (`TRANSPORT` §5.3 l.838). Two Core gaps remain under that pattern:
  1. **No synchronous stop / resource-release confirmation:** Unlike `unsubscribe` (which awaits `SubscriptionResult` and guarantees callback quiescence before returning, `INTERFACE` §2.5 l.1416–1420), cancelling and releasing an async `watch` call (`INTERFACE` §2.9.2 l.2041–2042: *"Release MUST NOT wait for provider execution or remote cancellation acknowledgement"*; `TRANSPORT` §6 l.857–858: best-effort `Cancel`) provides no synchronous confirmation that provider-side stream resources have stopped, forcing every streaming contract to add a separate `stop_watch(watch_id)` RPC if callers need deterministic teardown.
  2. **Slow-stream backpressure kills concurrent RPCs on the route:** `6cac8335` restricts `SubscriptionEnd` (`TRANSPORT` §5.1 l.753) strictly to `NOT_AUTHORISED`, and invocation-scoped events share the session's single ordered stream; if one slow `watch` consumer exhausts callee output buffering (`TRANSPORT` §5.2 l.792–801), the callee must either stall publication or close the entire Transport connection — aborting all concurrent unary RPCs multiplexed on that route.

#### `GC-05` — Browser and browser-extension environments cannot connect to any Core Transport profile or host WASM modules
- **Core specs:** `TRANSPORT` §8.4 l.1177–1317 (specifically `l.1217` & `l.1298–1302`), §9.3 l.1372; `LOADER` §3 l.165–190; `BCP` §3.3 l.198–199.
- **Use cases affected:** Browser-extension wallets (MV3 service workers) and web/WASM applications connecting to a local desktop Logos daemon on `localhost` or to a remote enrolled Runtime, or running lightweight client/verifier modules inside a browser sandbox.
- **Core capability gaps:**
  1. **Every Core Transport profile is unreachable from browser sandboxes:** Core defines only `logos.local.unix-stream`, `logos.remote.tls-tcp` (raw TCP+mTLS, where `TRANSPORT` l.1217 mandates *"This profile MUST NOT send, negotiate, or require ALPN"*), and `logos.remote.quic` (raw QUIC v1 with `ALPN = logos.remote.quic` on stream 0, no HTTP/3 or WebTransport, `l.1298–1302`), leaving HTTP/WebSocket/WebTransport bindings undefined (`§9.3` l.1372). Browser sandboxes and MV3 extensions cannot open Unix domain sockets, ALPN-less mTLS TCP sockets, or custom-ALPN raw QUIC streams (`WebTransport` requires `h3` ALPN), requiring an external non-Core gateway even on the same machine.
  2. **No WASM module realization profile:** `LOADER` (`l.165–190`) and `BCP` (`l.198–199`) admit only native C ABI binaries (`direct_static`, `direct_dynamic`, `hosted_dynamic`).

#### `GC-06` — Mobile / single-process `direct_static` builds lack per-module read-only `resource` delivery in `_MODULE_init` and collide when multiple modules embed singleton language runtimes (e.g., Go `c-archive`)
- **Core specs:** `INTERFACE` §5.2 l.3639–3649 (`logos_module_init_input_t`); `PM` Appendix A l.1918 (`kind: "resource"`), §9 l.1189–1193, §12 l.1393–1405; `RUNTIME` §8 l.1319–1322; `SECURITY` §11.5 l.474.
- **Use cases affected:** Mobile (iOS/Android) and single-binary desktop deployments (`direct_static`) bundling modules that ship large read-only assets (such as ~84 MiB Circom proving circuits or multi-megabyte RISC0 guest ELFs) or combining multiple catalog modules implemented in Go (`c-archive`).
- **Core capability gaps:**
  1. **No read-only `resource` path or handle for `direct_static` modules:** For dynamically loaded libraries (`PM` §9 l.1189–1193), a deployment can locate package resources relative to the `.so`/`.dylib` via `dladdr`. In **`direct_static`** mode (`SECURITY` §11.5 l.474), all modules are linked into one host binary so `dladdr` resolves every module to the same executable, `PM` `runtime_handoff` (`l.1397`) carries only a single `module-binary` `artifact` (which does not exist as a standalone file in `direct_static`, colliding with `6cac8335` `RUNTIME` §8 l.1319–1322's `static-binding-mismatch`), and `logos_module_init_input_t` (`INTERFACE` l.3639–3649) supplies only mutable per-instance `state_dir` with **no** per-module read-only `resource_dir` for `kind: "resource"` package artifacts.
  2. **Singleton language-runtime collision in `direct_static`:** Multiple catalog modules built as Go `c-archive` static libraries cannot be linked into one `direct_static` iOS/Android host executable (duplicate Go `_runtime.*` symbols, GC, and signal handlers), while iOS forbids `hosted_dynamic` child processes (`SECURITY` l.474) — requiring either consolidating all Go modules into one Go archive or porting them to a runtime-free C-ABI language.

#### `GC-07` — Per-packet inline callbacks and repeated multi-megabyte binary blobs across isolated module boundaries
- **Core specs:** `LOADER` §4.1 l.200–201; `RUNTIME` §4.1 & §12; `TRANSPORT` §2.1 l.371–388 & §4.1 l.635–652; `INTERFACE` §1.6 l.447–470.
- **Use cases affected:** (1) Per-segment payload encryption/decryption hooks (including background repair retransmissions) and per-message RLN / Mix-RLN proof callbacks between a networking/messaging module and a crypto/application/LEZ module; (2) application modules (`amm`, `token`, `twap_oracle`) supplying multi-megabyte RISC0 guest ELFs (`program_elf` + `program_dependencies`) to a local execution-zone prover.
- **Core capability gaps:**
  1. **High-rate data-plane callbacks across `hosted_dynamic` processes:** Because `LOADER` §4.1 (`l.200–201`) keeps one instance per Module Host in this revision, isolating modules in `hosted_dynamic` turns every inline per-segment callback into a cross-process role-inverted RPC with full deterministic-CBOR serialization and BLAKE3 Merkle value-commitment hashing on both sides (`RUNTIME` §4.1, `TRANSPORT` §4.1), with no shared-memory data plane or co-located hosted-group placement.
  2. **No content-addressed / read-only blob handle for large immutable inputs:** Passing multi-megabyte guest ELFs by value on transaction calls incurs repeated 1 KiB-chunked BLAKE3 Merkle hashing (`TRANSPORT` §4.1 l.635–652) and hits the 16 MiB Transport frame limit when multiple dependency ELFs are combined, forcing each provider contract to invent its own stateful blob-caching/session protocol unless Core provides read-only artifact/blob handles.

#### `GC-08` — `PM` `contract_documents` (`6cac8335`) is omitted from `installed_package_record` and `runtime_handoff`, lacks schema-content retrieval, and `0.x` `compatible` ranges block minor `extends` upgrades
- **Core specs:** `PM` §4 l.253–260 & l.295, §5 l.778–787, §10 l.1181, §11 l.1228–1239, §12 l.1393–1420.
- **Use cases affected:** Client generators, package browsers, and Runtime pre-realization / facade validation inspecting contract schemas of installed or catalog packages; evolving `0.x.y`-versioned module ecosystems across minor `extends` releases.
- **Core capability gaps:**
  1. **Incomplete `contract_documents` plumbing:** Although `6cac8335` added `? contract_documents` to `manifest` (`PM` l.253–260), both `installed_package_record` (`l.778–787`) and `runtime_handoff` (`l.1393–1405`) **omit `contract_documents`** (unlike `configuration`, whose CDDL text is embedded directly into `runtime_handoff` at `l.1416`), and `PM` still provides no method returning the CDDL text of a `schema` artifact (`local_path` is not a guaranteed module-visible path, `l.1181`).
  2. **Unverified SemVer producer rules & `0.x` caret lockup:** `PM` §11 (`l.1239`) does not enforce SemVer contract preservation across releases unless consumers duplicate `requires` commitments into `package_dependency.contracts` (`l.295`), and `PM` §11 (`l.1228–1230`) defines `compatible` on `0.x.y` so `0.2.0` rejects `0.3.0` (`0.0.z` matches only `0.0.z`) with no `>=` range kind — preventing minor-bump `extends` upgrades while packages remain on `0.x` versions.

## 2. Sub-points from Section 1 neither refuted nor carried into `claude-spec-comments-4.md`

Five substantive sub-points inside the partially accepted items remain open in the `6cac8335` text and are absent from `UF-01`–`UF-63`:

1. **`GF-23.1` (first and third points — omitted from `UF-53`):**
   - **Missing target identity in `"the action"` (`CA` §3 l.166–218 vs §7 l.788–793):** `CA` l.793 defines `"the action"` specially **only** for `permission_scope` (`permission`) and `runtime_control_scope` (`runtime` + `contract`). For `provider_access_scope` (`l.166–180`), `contract` is not part of `"the action"` (`actions` holds `"call"`, `"establish-route"`, etc.; likewise `module_execution_scope` `l.194–205` has `"start" / "stop"` without `runtime`/`module`, and `remote_enrollment_scope` `l.207–212` has `"enroll" / "refresh" / "remove"` without `remote_runtime`). Under `CA` l.792 (*"contains a scope of the same kind and action as a requested scope, whatever constraints, methods, or events that scope carries"*), a consumer holding an active grant to `"call"` *any single contract `X`* covers `"call"` on *every completely ungranted contract `Y`*, forcing `CA` l.788 to return `scope-denied` instead of `not-granted` across the entire system.
   - **Existential vs universal multi-scope check (`CA` l.785–786 vs l.792):** `grant-revoked` and `grant-expired` test *"every requested scope"* (`l.785–786`), whereas `scope-denied` tests *"as a requested scope"* (`l.792`). In a two-scope execution check `[module_execution_scope(M), permission_scope(P)]` where `M` is allowed and `P` has no rule or grant at all, `l.792` returns `scope-denied` rather than `not-granted`.
2. **`GF-14.2` (name-selected facade with `expected_execution_revision` — omitted from `UF-41`):** `UF-41` covers `both selectors` (`RUNTIME` l.3524) and `provider + expected_execution_revision` (`l.3525`). When `start_module` or `stop_module` instead supplies **`module` (by name)** + `expected_execution_revision` and resolves to an authorized facade (`RUNTIME` l.3540: *"After an authorized selection of a facade by module name, a request carrying `expected_execution_revision` MUST produce `INVALID_PARAMS` without structured detail"*), `RUNTIME` §9.3.1 places Step 5 (`comparison of an expected revision, which produces stale-revision` with `current_revision`, `l.1819–1820, 1830`) **before** Step 6 (`l.1831`) — yet a facade omits `execution` (`l.3359`) and has no `current_revision` to compare or return.
3. **`GF-14.4` (`renew_route` / `close_route` forwarding inversion — omitted from `UF-63`):** `RUNTIME` §9.3.1 l.1836–1837 states that when forwarding `renew_route` or `close_route` for a route established through a target Runtime, *"the source Runtime does not authorize the method itself. The source Runtime MUST select the target Runtime only from the routes of the calling consumer, and it MAY decode and validate the request before forwarding it."* For a local route, Step 2 (`l.1827`: method authorization **before** Step 3 payload decoding) still binds the source Runtime — yet the source Runtime cannot determine whether `request.route` names a forwarded remote route or a local route without decoding the payload before Step 2, inverting Step 2 and Step 3 (`INVALID_PARAMS` vs `NOT_AUTHORISED`) when an unauthorized caller sends malformed CBOR.
4. **`GF-15.2` (callee repeated `Unsubscribe` after `SubscriptionEnd` — omitted from `UF-48`):** `TRANSPORT` §5.1 l.755 states: *"An Unsubscribe for a subscription that the callee has ended with a SubscriptionEnd MUST produce a successful SubscriptionResult."* Because l.755 does not retire that allowance on the **first** `Unsubscribe`, a second `Unsubscribe` for the same `id` still literally names a subscription that the callee ended with a `SubscriptionEnd` and succeeds, whereas a second `Unsubscribe` after normal deactivation fails with `INVALID_PARAMS` under `l.731`.
5. **`GF-23.3` (`provider_export_record` selectors — omitted from `UF-55`) & `GF-23.4` (`PM` §8 check order and revoked-signer `update_package` — omitted from `UF-40`):**
   - `provider_export_record` (`RUNTIME` l.1936–1940: `{ listener, provider, enabled }`) has no `module` or `instance` field, so under `CA` §3.2 l.305 (*"A present selector whose field the subject does not carry does not match"*), a `runtime_control_scope` narrowed by `modules` or `instances` can never authorize `list_provider_exports` or `set_provider_export` for that module's provider.
   - `PM` §8 l.1067 (*"stop at the first detected validation failure"*) and l.1074 (`manifest.cbor` schema mismatch -> `invalid-package`) state no ordering requirement placing §4.3 `manifest.cose` verification (`l.565` -> `unsupported-manifest`) ahead of `manifest.cbor` validation; and a no-op `update_package` when no newer version exists (`PM` §15 l.1706: *"succeeds with the current installed record and changes nothing"*) succeeds even when the installed record's signer has been revoked, contradicting `PM` §4.1 l.437 (*"After an anchor is removed or revoked, Package Manager MUST NOT use it for a new successful resolution, installation, update, or Runtime handoff"*).

## 3. Rebuttals and clarifications on six items in Section 2 and Section 4

1. **`GF-15.5` (Not refuted — receiver handling of `SubscriptionEnd.error.code != NOT_AUTHORISED` is unspecified):** The review addresses only what the callee commits (`TRANSPORT` l.753) vs what the local callback reports (`INTERFACE` l.1479), overlooking the **wire receiver** rule raised in `GF-15.5`. In `TRANSPORT` §1.3 (`l.231–235, 277–285`), `logos.transport.subscription-end` admits any `logos.error_code` (`1..9`) in `error.code`. If a peer sends `SubscriptionEnd` carrying `MODULE_ERROR` (or `NOT_READY`), neither `TRANSPORT` §3.4 nor §5.1 l.753–756 states whether the caller's Transport receiver MUST reject the frame with `ProtocolError INVALID_PARAMS` and close the session (enforcing `l.753`'s *"this revision defines no other cause"*) or accept it and pass `MODULE_ERROR` to `observe_subscription_end` under `INTERFACE` l.1479 (*"`MODULE_ERROR` for every other cause"*).
2. **`GF-25.3` first point (Not refuted for `tstr` — `logos_tstr_size_<n>_<n>_t` is conformant and breaks §3.8 round-trip):** The review cites `INTERFACE` l.926 (*"An exact-size byte string MUST NOT use a pointer-valued constraint typedef"*). That rule applies **only to `bstr`**, not `tstr` — an exact-size `tstr` *does* use a pointer-valued constraint typedef (`typedef const char* logos_tstr_size_64_t;`, `INTERFACE` l.907, l.2203). Neither `INTERFACE` §2.2 l.907–916 nor §3.1 l.2204 forbids `<min> == <max>` in `typedef const char* logos_tstr_size_64_64_t;`. Under §3.8 (`l.2580–2588`), C-to-CDDL (`l.2204`) maps `logos_tstr_size_64_64_t` to `tstr .size (64..64)`, `cdCDDLe` l.325 canonicalizes that to `tstr .size 64`, and CDDL-to-C emits `logos_tstr_size_64_t` in `H'`, changing the typedef identifier (and even for `bstr`, §3.1 l.2205 states no `min < max` check). Requiring `<min> < <max>` in §2.2 l.914 and §3.1 l.2204–2205 settles both.
3. **`GF-22.2` (Narrower point stands inside `RUNTIME` §3.4 l.575–577):** Agreed that `RUNTIME` l.3732 governs Runtime shutdown rather than `stop_module`. Within `stop_module` itself, however, when the graceful drain deadline expires (`failure: "cleanup-timeout"`, `l.575`) and Runtime escalates to `Loader.release{force: true}` (`LOADER` §9 l.579: *"does not prove that module code completed cooperative cleanup or that destruction returned"*), `RUNTIME` l.576–577 (*"When the pending cleanup then completes, the explicit stop completes successfully. A cleanup failure during an explicit stop transitions the instance to `error`"*) does not state whether forced kill counts as completion (`stopping -> unloaded`, erasing `cleanup-timeout` per `l.3611`) or cleanup failure (`stopping -> error`).
4. **`GF-24.1` (Editorial template-substitution hazard in `INTERFACE` l.1253):** Agreed that in C's type system applying `const` to a typedef of `const char*` yields `const char* const`. Because generated headers emit no typedef for `tstr` (`INTERFACE` l.885 maps `tstr` directly to the token sequence `const char*`) and `<...>` elsewhere in §2.1–§2.4 denotes token substitution, pointing Rule 9 (`l.1253`) to the §2.3 `l.974–976` element pointer form avoids naive generators emitting `const const char**`.
5. **`GF-10.2` (Editorial — belongs alongside `UF-30`):** Agreed that `INTERFACE` l.3227, l.3241–3242, and l.3249–3250 determine the runtime `logos.schema` result for an extended-contract route; `INTERFACE` §5.1 l.3228–3234 and `RUNTIME` §2.4 l.407–408 still enumerate only primary concrete and implemented interface routes, the same incomplete two-case wording tracked by `UF-30`.
6. **`GF-15.4` (Narrower — optional vs required wire `Unsubscribe`) & `GF-08` (`UF-28` — behavioral release blocker, not merely editorial):**
   - On `GF-15.4`: Agreed that no rule *forbids* a caller binding from sending one wire `Unsubscribe` when locally ending an overflowing subscription (`INTERFACE` l.1473); the point is only that nothing *requires* it, so compliant callers may leave the subscription active at the callee for the life of the session.
   - On `GF-08` (`UF-28`): Together with `PM` §11 l.1236 (*"A release within the range that a `compatible` requirement on an earlier release accepts MUST provide every contract that the earlier release provides"*), `COMMITMENT` §9.1 l.963 and l.972 do not merely leave a consequence unstated — they prevent any concrete module that has a primary contract `P_1` and implements an interface `I_1` from upgrading to a compatible extension `I_2` in a minor release (`1.1.0`) without dropping `P_1` and violating `PM` l.1236.
